# Задача: чистый рестарт wasm-слоя форка «снизу вверх», через таргет-конфиг

Статус: SPEC / задание на реализацию. Основание: история форка (`git log`),
анализ текущих точек ветвления ядра и проверенные факты о
`wasm32-unknown-unknown`.

## 0. Краткая сводка

История форка показывает болезненную схему адаптации под wasm: сначала серия
коммитов с тяжелой переконфигурацией ядра (`16edc196`: 752 вставки в 5 файлах,
из них `Cargo.lock` на 948 строк; вендоренный `shim/page_size`; отказ от
`wee_alloc`; отключение `wasm-opt`), затем задача сведения изменений до
минимума (`b8bbf5f6`: `fts-cangjie` — 29 строк, ядро почти не тронуто). При этом
сегодня в `cozo-core/src` **52 точки `cfg(target_arch = "wasm32")`**, а
точность уже достигнута (сборка зеленая, `pkg/` собран и проверен пробами —
см. `cozo-lib-wasm/docs/wasm-script-notes.md` и `wasm-gap-report.md`).

**Тезис задания:** текущий набор `cfg(target_arch)` — это нормально, и чистить
его не надо. А вот три системные проблемы истории — переконфигурация ядра ради
сборки wasm, дублирование точки truth для признаков и смешивание волн фиксов —
решаются иначе: **точкой truth становится `cozo-lib-wasm/Cargo.toml` + конфиг
таргета wasm32**, а ядро получает не 52 ad-hoc ветки, а один платформенный
примитив (часы) и одну модель владения тредами. Всё ниже — как это сделать,
не ломая то, что уже работает.

**Граница задания (что НЕ трогаем):**
- `wasm-script-notes.md` и `wasm-gap-report.md` — источник истины о трепах,
  уже переписаны и зафиксированы (2026-09-26, пробы на `pkg/`);
- текущие `cfg(target_arch)` в ядре — не удаляем и не «расчищаем»;
- история git — не переписываем, только идём вперёд (см. §5 про ветки).

## 1. Ключевое наблюдение (проверено, а не предположено)

**Про потоки на `wasm32-unknown-unknown`.** Да, nightly у нас есть
(`1.100.0-nightly (5ceaf6608 2026-09-25)`, компонент `rust-src` установлен), и
да, многопоточность на обычном таргете технически собирается — но это не
отменяет факт из исходников `std`, а уточняет цену. Ветка
`all(target_family = "wasm", target_feature = "atomics")`
(`library/std/src/sys/thread/mod.rs:98-104`) берёт из `wasm` только `sleep`;
`Thread` и `available_parallelism` идут из `unsupported` в обеих ветках
(`_ =>`, строки 118-121). Атомики включают `Mutex`/`Condvar`/`Once` (см.
`sys/sync/*`: `wasm + atomics`), но рабочие потоки появляются **только** через
отдельный рантайм-механизм: nightly + `-C target-feature=+atomics` +
`-Z build-std` + shared memory + `wasm-bindgen-rayon::init_thread_pool` из JS +
COOP/COEP-заголовки сервера.

**Что это меняет для плана:**

- Таргет прежний — `wasm32-unknown-unknown` (верно). Но «потоки» — это не флаг в
  общей сборке, а **третий флейвор артефакта** со своим тулчейном, пайплайном и
  потребителем (Vite-демо с воркерами).
- Факт про rayon при этом остаётся: `rayon-core 1.13` (в локе) имеет
  задокументированный single-thread fallback (`src/lib.rs:22-37`), то есть ни
  один `par_iter` в ядре и в `graph`/`graph_builder` не паникует **уже на
  обычном stable-билде**. В threads-флейворе те же вызовы начнут реально
  распараллеливаться после `init_thread_pool` — код ядра при этом не меняется.
- `Instant`/`SystemTime` — заглушки с паникой при любых флагах тулчейна.
  Через `Cargo.toml` это не переопределить: `std` — не крейт, а часть тулчейна;
  `[patch]`/`features` управляют только графом crates.io. Шим часов (волна R1)
  нужен в любом флейворе.

Существующие данные, подтверждающие это направление:

- rayon уже безопасен на обычном таргете: `rayon-core 1.13` (в локе) имеет
  задокументированный single-thread fallback на wasm32
  (`rayon-core-1.13.0/src/lib.rs:22-37`) — ни один `par_iter` в ядре и в
  `graph`/`graph_builder` на этом пути не паникует. Проверено чтением исходников
  залоченных версий, не предположением.
- Единственный `graph`-алгоритм, вызываемый ядром, — `page_rank`
  (`fixed_rule/algos/pagerank.rs:54`); остальное — только CSR-типы. У `page_rank`
  кроме `Instant` есть `std::thread::scope` (`page_rank.rs:127-131`) — вот его и
  придётся переписывать при вендоринге, и atomics тут ничего не меняют.
  (✅ переписано в сессии 7 — см. статус в конце §3.2.)
- `query/eval.rs` уже имеет `cfg`-развилку на последовательную ветку
  (`:267/:298`, `:358/:389`), а `query/eval.rs:19` — единственный
  `#[cfg(all(not(wasm32), feature = "rayon"))]`: ядро **уже умеет** жить без
  rayon-пула. Паттерн правильный, его и масштабируем.

## 2. Что именно болит в истории (факты, не мнения)

1. **Переконфигурация ядра ради сборки wasm.** Перед `16edc196` сборка была
   сломана, и чинилась она в основном *вокруг* ядра: `cozo-lib-wasm/Cargo.toml`
   (+61/−?), вендоренный `page_size` (214 строк нового кода), обновление всего
   `Cargo.lock`. Само ядро тогда почти не трогали (правильно), но цена — 752
   строки «вокруг», которые теперь надо поддерживать (шим `page_size`,
   `nanorand`+`getrandom` 0.2/0.3 хаки, `wasm-opt = false`).
2. **Две правды о признаках.** `cozo-core/Cargo.toml:32`
   `compact-single-threaded = ["minimal", "requests", "graph-algo"]` — декларация
   без механизма: ни один потребитель в репозитории его не включает (grep:
   только 6 `.toml`, все — другие байндинги/бин, ни одного включения), а разница
   с `compact` не закодирована нигде (`graph-algo = ["graph", "rayon"]`
   безусловно тянет rayon, и именно он ломает `graph_builder 0.4.x` при
   `rayon ≥ 1.11` — см. комментарий у `cozo-core/Cargo.toml:192-196`). Ровно это
   место и должно стать точкой truth для wasm (см. §3.1).
3. **52 точки `target_arch` — не болезнь, а симптом отсутствия примитива.** В
   `runtime/` их 26, в `lib.rs` 10, в `data/` 9, в `query/` 5, в `parse/` 2.
   Половина — это один и тот же вопрос «есть ли часы / треды», заданный в лоб.
   Чистить их по одной — значит плодить волны правок, которые конфликтуют (та же
   ошибка, что и смешивание волн C5/C6 в gap-репорте, правило 1).
4. **Граница workspace уже есть, но не используется.** `cozo-lib-wasm` исключён
   из корневого workspace (`Cargo.toml`, секция `exclude`) и имеет собственный
   `Cargo.lock` — то есть это уже отдельный артефакт со своим графом
   зависимостей. Но `[patch.crates-io]` там живет ad-hoc (только `page_size`), а
   политика «что вендорим и почему» нигде не записана.

## 3. Целевое состояние и план (волнами, как в gap-репорте §«Fix sequence»)

Принципы, которым должен удовлетворять каждый шаг: **ядро меняется только
добавлением нового опционального механизма, никогда — переписыванием
существующего под wasm**; точка truth для wasm-сборки — `cozo-lib-wasm/`
целиком (манифест + `.cargo/config.toml` + профиль); каждая волна верифицируется
пробами из `cozo-lib-wasm/tests/probe/probe.mjs` (21 кейс) до/после.

### 3.1. Волна R0 — точка truth для признаков (без кода, только манифесты)

**Задача:** сделать `cozo-lib-wasm/Cargo.toml` единственным местом, отвечающим
на вопрос «что включено для wasm32», и завести недостающий механизм под уже
существующую декларацию `compact-single-threaded`.

Конкретно:
- Ввести в `cozo-core` признак `graph-algo-single-threaded = ["dep:graph"]`
  (зависимость от `graph` без `rayon`), а `graph-algo = ["graph", "rayon"]`
  оставить как есть. После этого `compact-single-threaded` получает реальный
  механизм: заменить в нём `graph-algo` на `graph-algo-single-threaded`
  (и поправить комментарий у `cozo-core/Cargo.toml:31`).
- Проверить, что весь граф `graph`/`graph_builder` собирается без rayon-пула в
  картину: `rayon` при этом остаётся в дереве транзитивно (его тянет сам
  `graph`), но **пул нигде не инициализируется нашим кодом** — на wasm это уже
  покрыто `cfg`-развилками `query/eval.rs` и последовательными ветками
  `hnsw_build.rs:252-275` / `relation.rs:1463-1490`. Отдельно зафиксировать в
  `wasm-build-notes.md`, что отключение rayon в `graph-algo` для wasm
  **намеренно не делается**: rayon-fallback задокументирован и безопасен
  (§1 выше), а удаление `rayon` из дерева потребовало бы патчить `graph`
  (у него `rayon` — безусловная зависимость), т.е. тянуло бы вендоринг раньше
  срока (см. gap-репорт, пункт 2, вариант B).
- В `cozo-lib-wasm/Cargo.toml` явно перечислить `features = ["wasm",
  "graph-algo"]` как сегодня, но добавить комментарий-точку truth: какой
  признак за что отвечает на wasm32 и куда смотреть при добавлении зависимости
  (`nanorand`/`getrandom` 0.2/0.3 прецедент — `wasm-build-notes.md` §1-2).
- Верификация волны: `cargo check --target wasm32-unknown-unknown` зелёный,
  все 4 host-сьюта зелёные, `wasm-pack build --target web --release` линкуется,
  21 проба — те же результаты, что до волны.

**Почему это «чище» истории:** вместо правок ядра под сборку — одна новая
опциональная фича-механизм и документированная точка truth; вместо неявного
«rayon есть, но мы его боимся» — явное решение с обоснованием.

### 3.2. Волна R1 — один платформенный примитив вместо 52 веток (ядро: только +)

**Задача:** ввести `cozo-core/src/runtime/clock.rs` — единственный модуль,
которому разрешено разговаривать со временем на wasm32
(`globalThis.performance.now()` через `js_sys::Reflect`, fallback
`Date.now()`; на хосте — реэкспорт `std::time::Instant`). Дизайн и список сайтов
— gap-репорт, пункт 4 (deadline-таблица уже там).

Правила волны (жёстко, это и есть «не ломать друг друга»):
- R1a (рефактор, поведения ноль): только замена типа `Instant` на
  `crate::runtime::clock::Instant` в ~8 файлах (`lib.rs`, `db.rs`,
  `transact.rs`, `imperative.rs`, `hnsw.rs`); `budget_now()` **продолжает**
  возвращать `None`. Проверка — host-сьюты + байт-в-байт те же 21 проба.
- R1b (одно поведение, одна строка): `budget_now() → Some`; проверка —
  `spbfs_timeout` даёт `eval::timeout` на wasm.
- R1c: `took` обратно (2 `cfg`), HNSW-таймер через шим.
- Ни одна из 52 существующих `cfg(target_arch)` при этом не удаляется.
  Удаление/консолидация — отдельная волна **только после** зелёного CI-гейта
  (иначе чистим то, что нечем проверить).

> **Статус (сессия 7, 2026-09-27):** единый `clock.rs` не вводили — вместо
> него точечные шимы: `web-time` в вендоренных `graph`/`graph_builder`
> (`cozo-lib-wasm-next/vendor/`, `[patch.crates-io]` только этого крейта),
> `js_sys::Date` в `stored_queries::create`, часы HNSW-профилирования выкл
> на wasm. `std::thread::scope` в `page_rank`/`triangle_count`/`edgelist`
> переписан на wasm-fallback в вендоре. Итог: 21/21 проба green.
> R1b (`budget_now() → Some`, живой `eval::timeout` на wasm) — открыто.

### 3.3. Волна R2 — треды: не «переконфигурировать ядро», а завести второй флейвор

**Задача:** зафиксировать, что single-thread wasm — основной артефакт, а
atomics/threads — отдельный флейвор со своим пайплайном, а не флаг в общей
сборке. Ночная сборка у нас уже есть (тулчейн и `rust-src` на месте), так что
ничего ставить не надо — только сконфигурировать и задокументировать флейвор.

Конкретно:
- R2a (доки + скелет, без nightly в основном пайплайне): в `wasm-build-notes.md`
  записать таргет-политику: основной таргет — `wasm32-unknown-unknown`, stable
  toolchain, без `-Z build-std`. `wasm32-wasip1-threads` для браузеров не
  использовать (несовместим с `wasm-bindgen` без полифилла; см. §1).
  Tool-слой: единая установка через rustup (`rustup target add
  wasm32-unknown-unknown` под обоими тулчейнами — проверено 2026-09-27:
  `nightly-2026-09-25` уже несёт `rust-src` и wasm32-таргет),
  `wasm-bindgen-cli` = версии `wasm-bindgen` в локе (старый крейт: 0.2.128;
  новый `cozo-lib-wasm-next/Cargo.lock`: 0.2.129; системный CLI сейчас
  0.2.114 — обновлять парой перед `wasm-pack build`),
  свежий `wasm-opt`/binaryen с флагами под фичи сборки
  (`--enable-bulk-memory`, для threads — ещё `--enable-threads --enable-simd`).
- R2b (сам флейвор — отдельный крейт `cozo-lib-wasm-next`, scaffold создан
  2026-09-27, см. `cozo-lib-wasm-next/README.md` и `WORKLOG.md`): собственный
  `rust-toolchain.toml` (nightly-2026-09-25, уже установлен вместе с
  `rust-src`; `wasm32-unknown-unknown` на nightly добавлен),
  `.cargo/config.toml` с `+atomics,+bulk-memory,+mutable-globals`, `+simd128`
  опционально (Profile: сравнить `opt-level "s"` vs `"z"` на сжатом размере;
  `panic = "abort"` — см. ниже), COOP/COEP-требование в демо, отдельная
  CI-джоба, собственный `Cargo.lock` (исключён из корневого workspace рядом
  с `cozo-lib-wasm`). Зависимости: `wasm-bindgen-rayon 1.3.0` (разрезолвлен
  в локе; требует `wasm-bindgen ^0.2.99` — в локе `0.2.129`, CLI
  `wasm-bindgen` обновить парой, системный сейчас `0.2.114`), плюс
  `init_thread_pool(navigator.hardwareConcurrency)` в демо до первого запроса.
  Статус: `cargo check --target wasm32-unknown-unknown` зелёный (с оговоркой:
  на Windows с глобальным `RUSTC_WRAPPER=sccache` сборка `web-sys` падает с
  `os error 206`, обход — `$env:RUSTC_WRAPPER=""`; см. WORKLOG session 2);
  `wasm-pack build` ещё не прогонялся. Ядро при этом не меняется.
  Старый вариант «флейвор внутри `cozo-lib-wasm/pkg-threads/`» отменён (см.
  §5: один крейт — один тулчейн — один `Cargo.lock`).
- R2c (размер/скорость, оба флейвора): сегодняшний release-профиль
  (`opt-level "z"`, без `panic = "abort"`) собран «как вышло», а не измерен.
  Заметки сообщества (сводка 2026 года) рекомендуют лестницу от дешёвого к
  дорогому: `panic = "abort"` (−10–20%, unwind-таблицы), `lto`, `codegen-units
  = 1`, сравнить `"s"` vs `"z"` (на сжатом размере разница часто минимальна, а
  скорость страдает от `"z"`), затем свежий `wasm-opt -Oz` (−15–20%), и только
  потом кодовые правки. Обязательные оговорки для этого репозитория:
  - `panic = "abort"` ломает `catch_unwind`, а он **есть**: ровно одно место —
    `cozo-core/src/runtime/graph_projection.rs:2383`, тестовый `catch_unwind`
    вокруг паникующего commit-fence (`a_panic_inside_the_commit_window_…`).
    Это тестовая страховка счётчика `inflight` — при `abort` тест надо
    переписать (или явно зафиксировать решение «профиль без abort для тестов»).
    Других `catch_unwind` в `cozo-core/src` и `cozo-lib-wasm/src` grep не
    находит (в `aggr.rs` — только упоминания в комментариях).
  - Замерять `twiggy top` надо **до** `strip` (нужна `names`-секция) и сравнивать
    размеры **после gzip/brotli** (`wasm-build-notes.md` §6 уже меряет так).
  - В `cozo-lib-wasm/Cargo.toml` уже есть `wasm-opt = false` для
    `wasm-pack.profile.release` — при уходе от wasm-pack (см. R2d ниже) это
    правило должно переехать в ручной вызов `wasm-opt` с нужными
    `--enable-*`, иначе свежий rustc-байткод опять сломает старый бинарник.
- R2d (инструменты, по желанию — не блокер): `wasm-pack` формально
  заархивирован upstream (июль 2025); функции распределены между
  `rustup`/`wasm-bindgen-cli`/`wasm-opt`/бандлером. Миграция не обязательна
  (пайплайн зелёный), но если делать — то вместе с заведением флейвора R2b,
  одним коммитом инфраструктуры, а не «между делом». Кандидаты: `trunk`
  (dev-сервер + hot-reload + COOP/COEP-заголовки из коробки) или голый
  `wasm-bindgen-cli` + npm-скрипты.
- Отдельно: `WASM_THREADS`/`MNESTIC_INDEX_BUILD_THREADS`-подобный
  рантайм-переключатель не вводить, пока нет потребителя — YAGNI, иначе получим
  третью правду о тредах рядом с `build_threads()` и
  `compact-single-threaded`.

## 5. Ветки и порядок слияния (обновлено: `wasm-next` вместо флейвора в старом крейте)

TL;DR истории: склейка stable-тулчейна, nightly-флагов, feature-дерева
(`graph-algo = ["graph", "rayon"]` тянет лок `rayon 1.10` / `wasm-bindgen
0.2.128`) и `wasm-bindgen-rayon 1.3.0` (хочет `wasm-bindgen ^0.2.99`, `rayon
^1.8.1` + `web_spin_lock`) в одном `cozo-lib-wasm` — это и была та боль, после
которой проще завести отдельный крейт. Правило: **один крейт — один тулчейн —
один `Cargo.lock`**.

- `cozo-lib-wasm`: заморожен (single-thread, stable, `pkg/`); maintenance —
  только критические фиксы трепов.
- `cozo-lib-wasm-next` (новый крейт, см. R2b в §3.3): nightly `1.100.0`
  (тулчейн и `rust-src` на месте; `wasm32-unknown-unknown` на nightly добавлен),
  atomics/SIMD, `wasm-bindgen-rayon 1.3.0`, свой lock, `init_thread_pool` из
  демо; исключён из корневого workspace рядом с `cozo-lib-wasm`.
- Основная ветка живёт на stable + `cozo-lib-wasm`; threads-линейка — на
  nightly + `cozo-lib-wasm-next`. Пересечение — только `cozo-core`, без правок
  под конкретный тулчейн.

Порядок веток:

- `chore/wasm-r0-feature-truth` (только §3.1) → `main`.
- `feat/wasm-r1-clock-shim-a` (§R1a, без поведения) → `main`; затем
  `feat/wasm-r1-clock-shim-b` (R1b+R1c, поведение) → `main`.
- `feat/wasm-next-scaffold` (новый крейт + конфиг R2b; nightly — только его
  джоба) → `main`. **Инвариант: stable-сборка (`cargo check`, host-сьюты,
  `cozo-lib-wasm`) обязана оставаться зелёной; nightly-сборка нового крейта
  проверяется только своей джобой и никогда не блокирует stable.**
- `docs/wasm-r2-threads-flavor-policy` (§3.3) → `main`.
- R3 — только после пунктов 6-7 gap-репорта; отдельной веткой.
- R2b/R2c/R2d — только когда появится потребитель threads-демо; R2a — сразу,
  это доки.
- Каждая ветка: host-сьюты (4 шт., 30 тестов) + `cargo check --target
  wasm32-unknown-unknown` + прогон 21 пробы; diff-ревью — сверить, что в
  `cozo-core/src` нет удалённых `cfg` (R0-R2) и нет новых `target_arch`-веток

## 6. Критерии приёмки задания

1. `cozo-lib-wasm/Cargo.toml` + комментарий в нём отвечают на «что включено для
   wasm» без чтения ядра; `compact-single-threaded` имеет механизм, а не только
   декларацию (R0).
2. Поведение не изменилось: 21 проба на `pkg/` — те же результаты, что
   зафиксированы в `wasm-script-notes.md` (R0, R1a); затем `spbfs_timeout` →
   `eval::timeout` и `has_took: true` (R1b, R1c).

   удалённого — до волны R3.
4. `wasm-build-notes.md` содержит таргет-политику (unknown-unknown — основной;
   wasip1-threads — нет; threads-флейвор — отдельный артефакт позже),
   `wasm-gap-report.md` §«Fix sequence» дополнен ссылкой на это задание как
   R-волны поверх C-волн.
